Update repo data workflow

Runs scripts/generate_data.py on a GitHub-hosted runner and opens (or updates) a pull request from auto/update-repodata into master containing only changes under data/. Nothing reaches master until someone merges that PR.

GITHUB_TOKEN

What it is

GITHUB_TOKEN is a token GitHub creates automatically at the start of every workflow job. You never create, store or rotate it.

  • Scope: only the repository the workflow runs in.
  • Lifetime: expires when the job finishes (24 hours at most).
  • Permissions: exactly what the workflow's permissions: block grants. Without the block, the repository default applies (read in this org).
  • Identity: acts as github-actions[bot], so PRs it opens are authored by the bot.
  • No chaining: pushes and PRs made with it do not trigger other workflows. This prevents workflow loops, but it also means CI (on: pull_request) will not run on the data PRs.

actions/checkout and peter-evans/create-pull-request both use it by default, so the workflow never references it explicitly.

How it is allowed in this repo

Two things must both be in place.

  1. Org (or repo) setting: allow Actions to create PRs.
    Org Settings → Actions → General → Workflow permissions → tick Allow GitHub Actions to create and approve pull requests. The repo has the same setting under its own Settings → Actions → General; the org setting must allow it first.
    Without it, PR creation fails with GitHub Actions is not permitted to create or approve pull requests.
    Check it with: 
    gh api repos/woodez-kubernetes/test-update-repodata/actions/permissions/workflow
# {"default_workflow_permissions":"read","can_approve_pull_request_reviews":true}
  2. permissions: block in the workflow. The default token is read-only, so the workflow grants itself write access: 
    permissions:
  contents: write        # push the auto/update-repodata branch
  pull-requests: write   # open/update the PR

Compared with a personal access token (PAT)

The workflow previously used the org secret GITOPS_PUSH_TOKEN and was switched back to GITHUB_TOKEN because the built-in token is safer.

Triggering with the gh client

Run these from inside a clone of the repo, or add --repo woodez-kubernetes/test-update-repodata.

# Start a run
gh workflow run update-repodata.yml

# Deterministic output: fixed timestamp and seed, so a re-run produces no diff
gh workflow run update-repodata.yml -f noop=true

# Follow the latest run until it finishes
gh run watch $(gh run list -w update-repodata.yml -L1 --json databaseId -q '.[0].databaseId')

# List recent runs (shows trigger event and who started them)
gh run list -w update-repodata.yml

# Show what the run did with the PR (created / updated / none)
gh run view --log $(gh run list -w update-repodata.yml -L1 --json databaseId -q '.[0].databaseId') \
  | grep "PR operation"

# See the data PR and its diff
gh pr list --head auto/update-repodata
gh pr diff auto/update-repodata

# Merge the data PR
gh pr merge auto/update-repodata --merge

gh needs to be logged in (gh auth login) as a user with write access to the repo.

Triggering with the .trigger file

Pushing a change to .trigger on master starts the workflow. The file's content does not matter; it only has to change, so write the current time into it:

git checkout master && git pull
date -u +%Y-%m-%dT%H:%M:%SZ > .trigger
git commit -am "Trigger data update"
git push

What happens next

  1. GitHub sees a push to master that touched .trigger and starts the workflow.
  2. The runner checks out master and runs scripts/generate_data.py in normal mode (the noop input exists only for manual runs).
  3. The data PR on auto/update-repodata is created, or updated if one is already open. Your .trigger commit is already on master, so it is not part of the PR.
  4. Merging the data PR changes only data/, so it does not start another run.

Which pushes start a run

PushStarts a run?
You change .trigger on masterYes
Workflow pushes to auto/update-repodataNo

You change scripts/generate_data.pyNo
README, workflow or other editsNo

Notes

  • The change must land on master. Editing .trigger on another branch does nothing until it is merged.
  • Each trigger adds a commit to master. If master becomes protected, every trigger needs its own PR, and gh workflow run is the simpler option.
  • After changing scripts/generate_data.py, trigger a run manually or with .trigger.
