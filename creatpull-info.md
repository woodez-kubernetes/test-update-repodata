# peter-evans/create-pull-request

The [`update-repodata`](.github/workflows/update-repodata.yml) workflow uses
[`peter-evans/create-pull-request`](https://github.com/peter-evans/create-pull-request) to turn
the files generated by the workflow into a pull request.

## Who maintains it

Peter Evans (GitHub user [`peter-evans`](https://github.com/peter-evans)) is an individual
open-source developer, not GitHub and not a company. He maintains several widely used actions,
including `create-pull-request`, `repository-dispatch` and `create-or-update-comment`.

## Is it normal to use?

Yes. It is one of the most widely used third-party actions and the standard answer to "change
files in a workflow, then open a PR". Common uses are dependency bumps, generated files and
documentation updates. Not every team uses it, but it appears in a large number of repos,
including well-known open-source projects.

## What it handles for us

The branch, commit and PR logic that is tedious to get right by hand:

- Detecting whether anything actually changed.
- Creating or resetting the branch (`auto/update-repodata`), committing and force-pushing.
- Updating an existing open PR instead of opening a duplicate.
- Doing nothing when the generated files match what is already there.

How we use it:

```yaml
      - name: Create or update PR
        id: cpr
        uses: peter-evans/create-pull-request@22a9089034f40e5a961c8808d113e2c98fb63676 # v7.0.11
        with:
          branch: auto/update-repodata
          base: master
          add-paths: data/**
          commit-message: "Update repo data"
          title: "Update repo data"
          body: "Automated data update from the `update-repodata` workflow (run ${{ github.run_id }})."
          delete-branch: true
```

No `token:` is set, so it uses the built-in `GITHUB_TOKEN` (see [info.md](info.md)). Its outputs
`pull-request-operation` (`created`, `updated`, `closed` or empty) and `pull-request-url` are
printed in the workflow's Summary step.

## The catch: trust

It is third-party code, and the workflow hands it a token that can push to the repo and open
PRs. Two safeguards:

1. **Pin to a commit SHA, not a tag.** A tag like `@v7` can be moved to point at different
   code; a commit SHA cannot. The trailing comment records which release the SHA is.
2. **Keep the token narrow.** Using `GITHUB_TOKEN` limits it to this repo, for one job, with
   only the permissions in the workflow's `permissions:` block.

### Updating the pinned version

Find the commit for a release tag and replace the SHA and comment in the workflow:

```sh
git ls-remote https://github.com/peter-evans/create-pull-request.git 'refs/tags/v7*'
```

For annotated tags, use the `^{}` line, which is the commit the tag points to. Dependabot can
also keep pinned SHAs current; add `.github/dependabot.yml`:

```yaml
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
```

## Alternative: do it with gh, no third-party action

The same job can be done with `git` and `gh`, which are already on GitHub-hosted runners:

```yaml
      - name: Create or update PR
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git checkout -B auto/update-repodata
          git add data/
          git diff --cached --quiet && { echo "No changes"; exit 0; }
          git commit -m "Update repo data"
          git push -f origin auto/update-repodata
          gh pr view auto/update-repodata --json state -q .state 2>/dev/null | grep -q OPEN \
            || gh pr create --base master --head auto/update-repodata \
                 --title "Update repo data" --body "Automated data update"
```

This removes the dependency, but we would maintain the edge cases ourselves. For example, this
version compares against `master`, not the existing PR branch, so re-running with unchanged
output still force-pushes a new commit to the open PR.

## Decision

Keep `peter-evans/create-pull-request`, pinned to a commit SHA. This is what most
security-conscious teams do: the action is well maintained and handles the edge cases, and
pinning removes the risk of the tag being moved.
